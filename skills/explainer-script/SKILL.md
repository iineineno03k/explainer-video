# 解説動画の台本を書く

引数: 資料のパス (複数可)・聞き手 (例: 開発チームに入ったばかりの人)・見終わって知っていてほしいこと。足りないものは資料から自分で決める。聞き手と「知っていてほしいこと」だけは、決められなければ聞く。

## 道具

`explainer` コマンド (このリポジトリ) を使う。PATH になければ入れる。

```bash
uv tool install git+https://github.com/iineineno03k/explainer-video   # 以後 explainer で動く
explainer check                                                        # VOICEVOX エンジンにつながるか
```

エンジンが動いていなければ、README の「VOICEVOX を動かす」(Docker か VOICEVOX アプリ)。台本の書き方の全部は README の「台本の書き方」。

## いちばん大事なこと：見る人の認知負荷を減らす

聞き手は資料を知らず、動画は巻き戻さずに流し見される。台本・画面のどの判断も「**いま見ている人が、何を見て、何を覚えればよいかが 1 つに絞れているか**」で決める。

- **知りたいことを構造化して先に渡す**：何が分かる動画かを、最初の画面で問いの一覧として見せる。場面はその問いに 1 つずつ答え、最後に答えを並べ直す (下の 1)。
- **見る所を 1 か所に絞る**：画面の写し・図を出したら、話している所を必ず赤枠で囲む。台詞ごとに枠を動かす。枠の外は自動で暗くなる (`dim: false` で消せる)。何も囲まずに画面全体を見せたまま話さない。
- **図は見方から**：図を出したら、中身の前に「どう読むか」(左から右が時間、色が担当、矢印がお金の向き…) を 1〜2 台詞で言い、読む順に枠を動かす。
- **1 画面・1 台詞・1 場面に 1 つ**：言うことが 2 つになったら分ける。

## 1. 知りたいことを構造化する

- 「知っていてほしいこと」を、**見終わって答えられる問い** 3〜5 個にする (例:「これは何のためにある？」「誰が何を決める？」「どこで何が出てくる？」)。問いの下に、答えに要る小さな問いがあれば 1 段だけぶら下げる。
- 問いは「全体 → 部分」の順に並べる。最初の問いは、それが全体の中のどこにあって何のためにあるか。
- この問いの一覧を、最初の場面の `card` (`points` に問いを並べる) で見せる。2 つ目の場面から、場面を問いに 1 つずつ対応させ、場面の `title` は問いの形で書く。
- 最後の場面で、同じ問いの一覧に答えを 1 行ずつ付けて見せる (`card` の `reveal` で 1 つずつ出す)。
- 場面は 5〜12 個。1 本 5〜10 分 (台詞 1 本 ≒ 3〜5 秒、1 場面 ≒ 台詞 3〜8 本)。長くなるなら問いを減らすか動画を分ける。

## 2. 台詞を書く (掛け合いの決まり)

- **ずんだもん (`zundamon`)** は何も知らない役。聞き手が思いそうな素朴な疑問・取り違え・つっこみを、説明より**先に**言う。語尾は「〜のだ」「〜なのだ？」。
- **四国めたん (`metan`)** は説明役。結論を先に、短く答える。語尾は「〜よ」「〜わ」「〜の」。
- 台詞は 1 本 40 字以内を目安に、句点で切る。1 本に言うことは 1 つ。長い説明は、めたんの台詞を 2〜3 本に分ける。
- 数字・専門用語・固有名詞は、台詞で言うだけでなく画面にも出す (赤枠の `label`、カードの `points`、台詞の `point`)。
- 資料にないことは言わせない。推測は「〜らしいわ」「まだ分かっていないの」と、推測と分かる言い方にする。
- 前に出た言葉を指すときは、同じ言葉で言う (言い換えると別のものに聞こえる)。

## 3. 画面を決める

- 資料に画面の写し・図があれば `image` に使い、**話している所に `boxes` で赤枠を付ける**。枠は台詞ごとに `boxes` を書いて、話に合わせて動かす。座標は画像のピクセル (左上が原点)。
- 画面の写しは、見てほしい所が小さければ `zoom` で寄せる。縦長の帳票・広い画面は、話す所ごとに `zoom` を変える。
- 順に追ってほしいときは、`label` に「① 検索」「② 一覧」のように番号を付け、台詞の順に 1 つずつ枠を出す。
- 図を最初に出す台詞では、枠を付けずに「見方」を言ってよい。次の台詞から枠で順に追う。
- 画像がない場面は `card` (title・sub・points)。項目を 1 つずつ出すなら `reveal: true` と、台詞ごとの `upto`。
- 画像の座標は推測で書かない。画像を開いて位置を確かめる (要れば Python の PIL で寸法を見る)。
- 図を自分で描くときは、見方が 1 つに決まる形にする (流れは左から右、担当はレーン、強調は 1 色)。1 枚に載せる要素は 7 個まで。

## 4. 読みの辞書

- 資料の専門用語・英字・社名の読みを `readings.yaml` (表記: 読み) に書く。読みは ひらがな か カタカナ。用語は現場での呼び方に合わせる。
- 単漢字の読み違い (「画 (え)」が「が」になる など) は、その字を含む熟語 (画像・画面・動画) を先に辞書に入れてから、単漢字を入れる (長い表記から置き換わる)。
- 迷う語は、エンジンに読ませて確かめる: `curl -s -X POST "http://127.0.0.1:50021/audio_query?speaker=3&text=<URL エンコードした文>"` の `kana`。

## 5. 台詞のつながりをレビューする (サブエージェント)

書いた本人の読み直しでは、台詞を足したときの前後のずれ (何にも答えていない「そうよ」、まだ出ていない「同じ案件」) を見落とす。build の前に、**この会話を引き継がないサブエージェント**にレビューさせる。

- サブエージェントを 1 本立てる。渡すのは、この skill のフォルダの `review.md` のパス・台本のパス・「指示書を読んでその通りにレビューし、表で返す。台本は直さない」の 3 つだけ。台本を書いた理由や資料の説明は渡さない (視聴者と同じく、台本だけで判断させる)。
- 「直す」は全部直す。直さないものは、なぜ直さないかを返信に書く。「よくなる」と「迷う」は、直すかどうかを書いた人が選ぶ。
- 直したら、同じ指示で再レビューする。**回すのは 3 回まで**。3 回目の「直す」を直したら、もう回さずに build する。4 回目より後の「直す」は、ほとんどが前の回の直しで入れた台詞から出る。
- 直すときは、台詞を足すより、削る・短くするほうを選ぶ。足した台詞が次の回の指摘の元になる。
- 人の指摘で台詞を足した・入れ替えたときも、build の前にこのレビューをやり直す。
- 中身 (資料と合っているか・誰の話か) のレビューは、understanding-video の `review-content.md` か、案件の手順で別に回す。

## 6. 書き出す・確かめる

台本は使う側のリポジトリに置く (例: `videos/<名前>/script.yaml`、画像は同じフォルダの `images/`)。

```bash
cd videos/<名前>
explainer lines script.yaml     # 台詞を通しで並べる (読み直し・レビュー)
explainer preview script.yaml   # 音声なしで、台詞ごとの画を描く
explainer build script.yaml     # 音声・mp4・字幕 (SRT) まで
```

- preview の画を何枚か開き、**その画だけを見て、どこを見ればよいかが 1 か所に決まるか**を確かめる。赤枠の位置・ラベルの切れ・字幕のはみ出し (2 行まで)・カードの文字数も見て直す。
- build の後、出力の SRT と台本を見比べ、読みの辞書が要りそうな語 (英字・数字の単位・社名) を拾って足す。
- 人に見せるのは台本 (YAML) と preview の画 2〜3 枚、できた mp4 のリンク。mp4 は git に入れない (`out/` は commit しない)。チームが開ける場所に置く。

## クレジット

最後に「VOICEVOX:ずんだもん」「VOICEVOX:四国めたん」の画面を、道具が自動で付ける。消さない。ほかの話し手を足したら、その名前も自動で入る。動画を置く場所の説明にも同じ表記を書く。
